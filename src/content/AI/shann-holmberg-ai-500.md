一个能帮你发现想法、用你的声音写出初稿、发布它们、并从中学习「什么有效」的系统。它把我的账号在两周内带到 500 万曝光，两个月内带来 10 万收藏。

内容的好坏，取决于背后的人和系统。投入在选题与写作上的低努力，只会换来另一端低质量的内容。

这篇文章帮你迈出第一步，打造属于自己的内容护城河。

我打造了一个只为一个目标优化的系统：

> **可被收藏的内容（bookmarkable content）** 也就是那种发出足够多「价值」信号、让读者愿意按下收藏按钮、放进自己第二大脑留作参考的帖子。

## 你会从这篇文章得到什么

这里的每一节，都是你这周就能复制、改编、用在你自己账号上的东西。

- **完整的 Content OS 框架**，映射到今天就能搭建的真实文件夹
- **四个生产级的提示词**，可以直接粘贴进 Claude 或任何前沿模型开始产出
- **V1 起步包**，1–2 小时的准备工作，每周都能省下这些时间
- **写作者上下文包（writer context packet）模板**，把含糊的简报变成具体的初稿
## 先讲结果，再讲理论

我运营自己的 X 账号。在这次开始之前，这个账号只是挂了个名字、有几千粉丝，我基本没怎么用心打理它。

没有什么值得称之为「系统」的东西。只有零散的帖子，换来零散的数字。

然后我坐下来，搭出了这篇文章里的系统。

两周 500 万曝光——来自一个几乎沉寂的账号。之后每周迭代。到第二个月，同一个账号突破了 1100 万曝光和 10 万收藏。

我和朋友一起创立了 @LunarStrategy，我们在那里为我们的客户部署类似的 Content OS。

## 一条不可妥协的底线

在任何机制之前，先说整个系统依赖的那条规则：

绝不发布未经编辑的内容，每一稿都要亲手收尾。系统是加速器，不是自动驾驶。一旦被当作自动化工序来用，它就会衰退。

目标不是用提示词伪造一个「声音」，而是从你真实的写作中，沉淀出一个可复用的运营资产。做一次、持续更新，然后模型生成的每一稿都会更贴近你，你的时间就能花在打磨想法上。

## 「可被收藏」到底指什么

一枚收藏，是读者对未来自己许下的一个小承诺。它说的是「我以后还会用到这个」。这个门槛远比一个赞高，它在算法里的行为也完全不同。

我不想夸大排名的数学原理，但作为一个每周都这么干的运营者，规律是稳定一致的。收藏是对「未来价值」的一次投票，而那些赚到收藏的帖子，会在发布很久之后依然不断出现在信息流里。

在我发出任何东西之前，我都会问自己：这条帖子看起来像下面哪一种？

- 一份清单（checklist）
- 一份蓝图（blueprint）
- 一套文件夹结构
- 一个模板（template）
- 一个框架（framework）
- 一份分步工作流
- 一张带结论的证据截图
- 一组前后对比
- 一个可复用的心智模型
如果一稿不像上面任何一种，那它通常就不该发出来。

上下文存放在两个地方。

**信号层（signal layer）** 是你带进来的所有外部信息：你这周收藏的书签、你监控列表里创作者的内容、你读过的一篇文章。

**知识图谱（knowledge graph）** 是你已经拥有的全部内部资产：你的个人操作系统、笔记、日记、语音备忘，以及你已经发布的内容归档。

路由（route）决定哪个来源喂给简报（brief），而 **strategy（策略）+ voice（声音）+ stores（素材库）** 位于两者与写作者之间，让上下文经过筛选。

每一条帖子、文章、线程或 campaign 都会开启一个新的 run 文件夹。那个文件夹就是内容对象本尊。它从系统的共享部分拉取所需，走过一道道关卡的生命周期，并在发布时把学到的东西写回去。

一个内容对象的生命周期：

```
`captured
  → idea_review (route: original / repurpose / rewrite / research+ideate)
  → brief_ready
  → drafting
  → verification
  → shann_draft_review
  → approved
  → scheduler_ready
  → scheduled
  → published
  → feedback_24h
  → feedback_72h
  → learned`
```

围绕 run 文件夹摆放的东西：

**strategy（策略）。** 定位、受众、内容支柱、来源监控列表。这是唯一一层我靠手改。如果你让 AI 来写你的定位，那你就不叫有定位。你只有一堆「平均值」。

**voice（声音）。** 声音档案和 master avoid-slop 文档（避开 AI 腔的对照表）。每一个 agent 在写下任何一行之前都会先读它。

**stores（素材库）。** 原始输入收件箱、需要关注的工作板、想法 backlog、钩子库、证据库、反馈日志。这是 run 文件夹读取并回写的共享记忆。

**modules（模块）。** 写作者的 skill（SKILL.md、references、templates）。生产代码。你给系统分配一个角色，就对应一个模块。

**workflows（工作流）。** 推动内容对象在状态间流转的剧本：从想法到发布、验证者检查清单、调度交接、反馈闭环。

## 四条路线

在一个内容对象进入起草之前，想法关卡（idea gate）只做一件事：判断这是哪种内容？

四条路线，每条有自己的简报、自己的引用素材、自己的关卡：

**ORIGINAL（原创）。** 直接取材于你、或取材于你的第二大脑（个人 OS、笔记、日记、语音备忘、你攒了好几个星期的想法）。简报依赖你的根基：定位、证据库、内容支柱。不依靠外部来源。高品味投入。

**REPURPOSE（复用）。** 拿自己已有的内容做延伸。一个内容系列衍生、从你某篇文章抽出的一条线程、对一条爆款帖的自我引用（self-QRT）、或从你已发布作品里抽出一句话的推文。骨架是你的，格式在变。

**REWRITE（重写）。** 拿信号层的外部源素材（一条值得回应的推文、一篇值得拆解的文章、一段带着有用框架的转写），透过你的观点和声音转译出来。简报会明确写清楚：保留什么、如何署名、适用哪些声音规则（依据 master avoid-slop 文档）。

**RESEARCH + IDEATE（调研 + 构思）。** 在任何起草开始前，探索一个主题、研究规律、生成候选角度。它的输出不是一条帖子，而是一个被磨利的想法、或一串角度，回馈进 `stores/ideas/` 供后续生产。

每条路线仍然产出**一个** run 文件夹，并把路线声明在 `content-object.md` 里：

```
`runs/active/2026-05-bookmark-flywheel/
  content-object.md   # route, current state, next action
  idea.md             # the idea gate decision
  brief.md            # writer handoff (for original, repurpose, rewrite)
  draft-package.md    # rendered draft, verifier output, review notes
  feedback.md         # 24h / 72h learnings`
```

## 在这之前是什么

在现在的 Content OS 之前，我搭过一个 4-agent 系统，跑的是这个循环的早期版本：研究员、想法创造者、写作者，再加一个在它们之间路由的编排者。每个 agent 都有自己的记忆，跨会话持久。

整个东西是用 claude code 建的，用的是 markdown 提示词、一个数据库和一堆 CLI 工具。

> 嵌入推文: <[https://x.com/i/status/2028417727661318425>](https://x.com/i/status/2028417727661318425%3E)

它有效，但过度设计了。四个 agent，去处理结构上只是「三个生产步骤加一个反馈循环」的事。跑过它之后，我学到了大多数讲 agent 蜂群的博客文章都漏掉的东西：

> 关键杠杆从来不是 agent 的数量，而是喂给写作者的那层知识。

现在这套是更精简的版本：更少的 agent、更多的工作流、同样的循环、更锐利的产出。

**`runs/active/` 是心脏。** 里面每个文件夹就是一个内容对象。一条内容 = 一个 run 文件夹，那个文件夹自带自己的状态，直到它发布并归档。

## 你的 V1 起步包

计划 1–2 小时的准备工作。你不会做完，但你会**开始**——而「开始」是唯一值得存在的状态。你在这一步花的时间，会在之后每周以「节省数小时」的方式回报给你，因为下一稿是从上下文开始，而不是从零开始。

**第 1 步：搭好结构。** 创建六个顶层目录：strategy（策略）、voice（声音）、stores（素材库）、runs（运行）、modules（模块）、workflows（工作流）。在 runs 里加上 `active/` 和 `archive/`。其余暂时留空即可。

**第 2 步：填 strategy。** 打开 `strategy/positioning.md`、`strategy/audience.md` 和 `strategy/pillars.md`。每个写三到五行。内容支柱（pillars）是你「已经赚到资格」去谈论的三四个主题。受众（audience）是一个具体的人，而不是一个人群。

**第 3 步：写下声音锚点。** 放到 `voice/voice-profile.md`（5 条你始终遵守的规则、5 种你从不用的套路、2–3 条在你状态最锋利那天听上去像你的参考帖），并开始你自己的 `voice/avoid-slop.md`（用下面那节的八种模式当起点过滤器，每当有稿子漏过了一个破绽就往上加）。往 `stores/proof/` 里放十个具体证明——像数字、名字、你发布过的项目、亲身经历的案例。

**第 4 步：往 `stores/inbox.md` 里丢十个想法。** 一半应该来自你本月已经在 DM 或电话里说过的东西，而不是当场现编。

**第 5 步：为一个想法开一个 run 文件夹。** 创建 `runs/active/2026-05-{你的-slug}/`。在里面写 `content-object.md`（id、状态、格式、所属支柱）和 `brief.md`（下面那个写作者上下文包模板）。把简报交给你的写作模型。

**第 6 步：读稿并闭合循环。** 模型会在同一个 run 文件夹里返回 `draft-package.md`。拿它对照验证者和 master avoid-slop 文档检查。通过就批准并排队；否则用一条具体的意见退回去。发布后，写 `feedback.md` 并归档这个文件夹。

## 写作者上下文包（writer context packet）

这是大多数人搞错的地方。他们把整个品牌文档、整个知识库、整个时间线统统塞进一个提示词里。

模型写出来的就是安全的糊糊，因为上下文里没有一样东西是「承重」的。一个紧凑的包，几乎总是胜过巨大的上下文窗口。

这个包以 `brief.md` 的形式住在 run 文件夹里。每个内容对象一个包，在起草开始前写好。

复制这个模板：

```
`writer context packet
─────────────────────
thesis:        one sentence the post must prove
reader:        the specific person who should save it
proof:         numbers, screenshots, stories I am allowed to use
angle:         the unexpected framing
constraints:   format, length, tone, banned phrases
voice anchors: 2-3 lines that sound like me
risks:         what would make this read as slop or as cringe
open loops:    what I do not yet know, that the writer should flag`
```

## 可收藏性评分表（bookmarkability rubric）

在一稿接近排期之前，先给它打分。每项零、一或两分：

1. 为读者省下一件未来的事
2. 包含证据（数据、截图、点名的例子）
3. 给出一个可复用的收获（模板、清单、框架）
4. 有具体的受众和「待办事项（job-to-be-done）」
5. 不需要我在场也能被应用
6. 有一张强力的截图或视觉
满分 12 分。我个人的及格线是 8 分。低于 8 分，它回到包里，而不是进垃圾桶。大多数「糟糕」的初稿，其实是跳过评分表中某一行的好稿。补上那一行，重新评分，发布。

这套评分表也是训练新协作者最便宜的方式。你不需要抽象地教鉴赏力。你递给他们评分表，指三篇爆款帖，然后让分数自己说话。

## master avoid-slop 文档（避开 AI 腔对照表）

评分表告诉你一条帖子是否值得保存。avoid-slop 文档告诉你一条帖子是否像人写的。

我在每篇稿子发出前，都会用一份文档过一遍。它有 54 种模式，分为三个严重等级，每种都有具体改法。它能抓出像这样的东西：

```
`- promotional language ("groundbreaking", "game-changing")
- significance inflation ("pivotal moment", "testament to")
- vague attribution ("experts believe", "studies show")
- false agency ("the system compounds", "the data tells us")
- rhetorical setups ("the question is whether you X")
- staccato fragmentation ("no X. no Y. no Z.")
- em dash overuse (zero is the target)
- filler adverbs ("actually", "literally", "quietly")`
```

这是我在起草前让写作者 agent 加载、在批准前让验证者加载的文档。

**这就是「AI 写的」与「一个恰好用了 AI 的人写的」之间的差别。**

我现在还在系统内部打磨完整版，但上面这八种模式，已经足够开始把你的初稿里大部分 AI 腔过滤掉了。

## 四个可直接复制的提示词

简短、聚焦、并且本来就是要被改的。把它们当作起点形状，而不是魔法咒语。

每一个对应系统里的一层。把它们丢进 claude、gpt 或你用的任何前沿模型里。如果你只留一个，就留最后那个「事后复盘（postmortem）」版。

```
`prompt 1: brand foundation extraction
maps to: strategy/ + voice/

ROLE
You are helping me build the foundation layer of a personal-brand
content system. You will turn raw, half-formed notes about my
work, audience, and voice into a tight set of operating documents
my writer agent can use to draft in my voice.

INPUT
I will paste raw notes covering: what I do, who I help, what I
have shipped or built, how I sound when I write, the kinds of
people I want as readers, and anything I refuse to sound like.

PROCESS
1. Read the notes. Note any contradictions or gaps.
2. Ask me up to 5 clarifying questions. Do not skip this step.
3. Once I answer, produce the six artifacts in OUTPUT FORMAT.
4. Flag anything you had to invent or guess. Mark it "assumed".

OUTPUT FORMAT
1. positioning. one sentence. the line a stranger should be able
   to repeat back after one of my posts.
2. audience. one specific person, by role, situation, and stake.
   not a segment.
3. pillars. 3 to 4 topics I have earned the right to talk about,
   each with a one-line reason I am credible on it.
4. voice rules. 5 things I always do.
5. banned patterns. 5 things I never do.
6. proof bank. 10 concrete things I can reference (numbers,
   names, shipped projects, lived examples).

RULES
- If a section is generic, mark it "missing" and tell me what
  you need from me.
- Do not invent numbers, customers, or projects.
- Use my own words wherever possible. Lift phrases from the notes.
- The output should fit on one page. Tight is the point.`
```

```
`prompt 2: bookmarkability scoring
maps to: stores/ideas/ (idea gate)

ROLE
You are a critic who has read 10,000 high-bookmark posts and
1,000,000 forgettable ones. You can tell, line for line, what
makes a reader save a post versus scroll past.

INPUT
A post idea or a draft. Could be a one-line thesis, a rough
sketch, or a full draft.

PROCESS
1. Read it once for the surface read.
2. Score it 0, 1, or 2 on each row of the rubric below.
3. Total it out of 12.
4. If under 8, name the single row that would lift the score
   most, and how.

RUBRIC
- saves the reader a future task
- includes proof (numbers, screenshot, named example)
- gives a reusable takeaway (template, checklist, frame)
- has a specific audience and job-to-be-done
- can be applied without me being in the room
- has a strong screenshot or visual

OUTPUT FORMAT
- Total score: X / 12
- Strongest row: [row] (why)
- Weakest row: [row] (specific fix, in one line)
- Verdict: ship / fix and re-score / kill

RULES
- Do not pad the score to be encouraging.
- Do not suggest "make it more engaging." Tell me what to add or cut.
- If the idea is well below 8, say "kill" and tell me why directly.`
```

最后这个是整个系统里杠杆率最高的提示词。模型不能说「钩子很强」或「洞察很精彩」。

它必须指向具体的句子。大多数能通过验证者的初稿，仍然会卡在这个提示词上——而这两者之间的差距，正是真正的编辑所在。

## 两个模型，两种角色

一旦我开始规模化地跑这个系统，我碰到了一个事后看显而易见的点：

写作这件事，和运营系统这件事，是不同的工作，而且它们奖励不同的模型。所以我不再用一个模型包打天下。

我现在的分工是这样的：

**写作者（writer，opus 4.7）负责：**

- 品味
- 节奏
- 压缩
- 声音
- 实际的初稿
**编排者（orchestrator，gpt-5.5）负责：**

- 在层与层之间路由
- 为写作者打包正确的上下文
- 决定什么被传进来
- 跑验证者
- 向发布层交接
## 在哪里运行这套系统

这样的系统只有在编排者能干活时才有效。它需要能读写文件、调用工具、跑检查，并按排期把已批准的稿子交给发布层。所以真正的问题不在你用哪个应用，而在于系统住在哪里。

我见过两种跑得干净的方案。

**方案一：一台装了 claude code 的 VPS。** 你租一台小服务器，把 `/content-os` 文件夹放进一个 git 仓库，让 claude code 在上面跑工作流。你得到完全的控制权、一台完全属于你的机器、每周复盘用的定时任务、验证者用的脚本，还有一个能碰你同样那些文件的 AI 编码器。如果你喜欢拥有整套技术栈、又不介意在服务器上折腾，这就是你的路。

**方案二：hermes agent，也就是我现在用的。** 它就是为这种形态的工作而生的：agents、skills、工具访问、文件和 git 操作、浏览器和搜索、定时任务，以及贯穿整个工作流持久的上下文。把它指向你的根基、你的输入、你的包模板，编排层就在步骤之间扛起负担，这样我的时间就能花在写作和编辑上。初稿在发布前仍然会交到我手上。

两个都不是必须的。要紧的是那个原则：把系统托管到某个地方，让你的编排者能读写你的文件、调用它需要的工具、跑验证者，并把已批准的帖子交给 postiz。这两个里挑一个更贴合你工作方式的。

## 反馈闭环是一道护城河

大多数人停在「发布」这一步。而系统正是从这里开始赚回的。

我每周会看：

- 浏览量（views）
- 收藏数（bookmarks）
- 收藏率（bookmark rate）
- 回复数（replies）
- DM 跟进（DM follow-ups）
> 收藏率是我最看重的那个。它告诉我哪些帖子赚到了「保存」，而不只是赚到了「滑过」。

爆款被复制进 inputs 当成例子，旁边写着它们的数字。扑街的则去更新声音规则、禁用模式或想法过滤器。

因为这一周学到的东西，下一份包会更锋利。
